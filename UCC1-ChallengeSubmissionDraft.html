Problem Statement — What problem does this solve?

Every week before the US Public Sector IBM GM meeting, our Sales VP manually exports the pipeline from IBM Sales Cloud (ISC), copies deal data into a spreadsheet, writes a narrative summary by hand, and builds a PowerPoint deck. This process takes 60–90 minutes every single week and is error-prone because it's done under time pressure with no automated change detection.

There is no built-in way to see what changed week-over-week: which deals were promoted to the next stage, which slipped their close date, which dropped out of the pipeline entirely, and which new deals appeared. That comparison exists only in the VP's memory — and if memory is wrong, the GM meeting is based on stale intelligence.

The deeper problem is structural: IBM Sales Cloud is protected by IBM w3id SSO with passkey authentication that blocks every programmatic access attempt. Seven different technical approaches were tried and documented — Playwright automation, cookie injection, CDP interception, Salesforce REST API calls — all blocked by IBM's own security model. The data lives behind glass that IBM has not opened to its own employees via API.

The result: a Sales VP spends 90 minutes every week doing work that a machine should do, with no ability to automate it through official channels.

Solution Description — What does your solution do and how does it work?

ISC Automated Sales Forecast is a Node.js/Express web application — multi-user, IBM-SSO-authenticated — that integrates with IBM watsonx.ai to automate the entire weekly GM meeting prep workflow for any IBM Sales leader.

Data ingestion: Because IBM Sales Cloud blocks programmatic API access, the app uses a practical workaround: the VP exports a HAR file from Chrome DevTools (a 90-second step), which the app parses to extract all Open pipeline opportunities with full field fidelity. The app imports only active Open-stage deals (Engage → Negotiate) — Won, Lost, and statusless entries are excluded because they are not relevant to forecast preparation. The count in the app will always be lower than ISC's headline total, which counts all statuses; this is expected and correct.

AI scoring: Every opportunity is scored by ibm/granite-13b-instruct-v2 on IBM watsonx.ai, producing a confidence score (0–100) and a tier (High/Medium/Low) based on deal stage, close date proximity, next-steps health, and financial signals. Scores are persisted to SQLite so the diff engine can show before-versus-after confidence changes week over week.

GM narrative: meta-llama/llama-3-70b-instruct (hosted on IBM watsonx.ai) generates an executive-ready narrative scoped to whatever filter the VP has applied — for example, just Commit-stage deals in Q3, or just a specific geography. Ready to paste directly into GM meeting opening remarks.

Week-over-week diff engine: ibm/granite-3-8b-instruct generates a delta summary describing what changed: promoted deals, demoted deals, slipped close dates, amount changes, new deals, and removals. Each change category opens a drill-down modal showing affected deals with before/after confidence scores.

PowerPoint generation: One click produces a formatted PPTX with a cover slide (GM narrative), scored deal slides, and a "What Changed" slide. The VP walks into the GM meeting with a deck already built.

Permanent quarterly audit ledger (v2.3.0): A three-button confirm modal gives the VP full control: Cancel (do nothing), Generate Only (PPT only, no record written), and ✅ Confirm & Generate (PPT + immutable UUID-keyed baseline written permanently). Every "✅ Confirm & Generate" click appends one irreversible row-set to the baseline_ledger table, timestamped and quarter-tagged. The ledger is append-only — no DELETE or UPDATE paths exist. This is the same discipline as an auditable financial reporting system: once you sign off, that record is permanent.

"Today vs today" bug eliminated structurally: The diff engine compares live data against the most recent confirmed baseline using a strict confirmed_at < asOf SQL guard. Because the new baseline is written after the PPT is generated, it is physically impossible for the current run to select its own snapshot as the prior baseline.

Simulated IBM SSO + multi-tenant data isolation (v2.4.0): The app now supports multiple concurrent IBM users — TSLs, ATLs, and the GM — each with a completely isolated pipeline. Authentication uses the same OIDC session architecture as real IBM w3id SSO. Every database table is isolated by user_id. A simulated login page lets any of the 9 test users sign in with their real IBM email and a test password. Swapping to real IBM w3id requires changing one code block and setting two environment variables (Client ID + Secret from IBM app registration). The TEST MODE banner in the UI header makes it unmistakably clear which user is active during demo sessions.

Pipeline Intelligence Engine — Deal Health Card (v2.5.0–v2.5.7): A per-opportunity hygiene scoring system (0–100) built directly from the existing schema — no new data sources, no watsonx credentials required. Every deal gets a coloured health icon (red/amber/green) in the pipeline table. Clicking it opens a Deal Health Card modal with: a hygiene score broken down into 5 components (Next Steps presence, recency, Team Notes, forecast/score alignment, FLM agreement); auto-generated sentence-level action items for the VP (P1/P2/P3 priority); full Next Steps and Team Notes text; and a week-over-week timeline from the permanent audit ledger. A second tab shows the full Rep Hygiene Summary — 76 owners in Duey's pipeline ranked by coaching priority, with blank NS count, stale NS count, forecast mismatch flags, QE Close count, and average hygiene score — with a sticky header that stays pinned while scrolling. v2.5.6 adds padded-close detection: deals closing within 4 days of any quarter-end surface a P1/P2/P3 management signal at the top of the Deal Health Card action items. The engine directly addresses the three strategic management use cases: SR/SM/C behavioral tracking, hygiene as a risk signal, and absence of activity as a coaching/attrition indicator.

Carbon Design UI: IBM Carbon Design System throughout — IBM Plex Sans, Carbon tokens, status-driven action bar, user identity chip (avatar + display name + role + Sign Out), named view presets (GM Prep · At Risk · Full Pipeline), tri-state header checkbox, Match ISC View toggle, GM Ready indicator. Every action is independently re-runnable — no numbered sequence lock.

Built with IBM Bob: The entire application — 26 development sessions, 5,000+ lines of production code, all architecture decisions — was built collaboratively with IBM Bob (IBM's sanctioned watsonx AI development tool, listed as an official resource on the IBM internal "Build with watsonx" page).

Business Value — What is the measurable impact?

Time savings: 90 minutes of manual weekly work reduced to under 5 minutes — a 94% reduction. For one Sales VP, approximately 75 hours saved per year. Multiplied across IBM's US Public Sector sales organization, the impact scales significantly.

Quality improvement: The manual process was error-prone and memory-dependent. The automated process is consistent, reproducible, and AI-augmented — the GM narrative is generated from live pipeline data, not from what the VP remembered to include. The diff engine catches changes the VP would have missed.

Quarterly rep/manager analytics: The permanent audit ledger enables three new analytical capabilities that did not exist before v2.3.0: (1) SR/SM/Customer trajectory — track every deal's stage, amount, and confidence score across all 12–13 weeks of a quarter to surface rep-level pipeline performance patterns. (2) Next Steps hygiene analysis — deals with 3+ consecutive blank Next Steps weeks are statistically more likely to slip or drop; this leading indicator is now queryable in SQL against the full ledger. (3) Coaching signal detection — a sales rep with consistently blank Next Steps is either stalled on the deal or disengaged from the role; the pattern is now visible to the first-line manager before it becomes a performance problem.

Scale: Every IBM Public Sector Sales VP runs the same weekly GM prep workflow. This application is architected to run as a multi-user cloud service — and as of v2.5.17, it is a multi-user application, with 9 distinct users, IBM SSO architecture, full per-user data isolation, and a Pipeline Intelligence Engine that scores every deal and every rep on real pipeline data. The CIO "Build with watsonx" Path to Production has been identified as the official deployment path; a ServiceNow AI System Demand is being submitted as part of this challenge entry.

Financial forecasting: The week-over-week diff engine surfaces pipeline momentum in real time — deals accelerating toward close, deals slipping, deals at risk — giving GM meeting participants data-driven intelligence about forecast reliability, not just a static snapshot.

IBM watsonx Usage — Which watsonx products/models are used and how?

Three IBM watsonx.ai models, each performing a distinct function:

ibm/granite-13b-instruct-v2 — Opportunity confidence scoring. Each of 221 deals is evaluated, producing a confidence score (0–100) and tier (High/Medium/Low). Scores are persisted so the diff engine reports before/after confidence deltas week over week.

meta-llama/llama-3-70b-instruct (hosted on IBM watsonx.ai) — Executive GM narrative generation, scoped to the VP's current filter. Produces meeting-ready prose from live pipeline data.

ibm/granite-3-8b-instruct — Week-over-week delta summary. Receives the structured diff output and generates a concise narrative for the "What Changed" PowerPoint slide.

All three accessed via IBM watsonx.ai REST API. Graceful fallback: when credentials unavailable, the rules-based scoring engine runs and the app is fully functional in either mode.

IBM Bob (IBM's watsonx-powered AI development assistant) built the entire application across 29 sessions.

Innovation — What is novel or creative about your approach?

Solving IBM's own auth wall with ingenuity: IBM Sales Cloud blocked every programmatic access attempt across seven documented technical approaches. The HAR export solution turns IBM's own security posture into a feature — data is exported from an already-authenticated browser session, requiring no credentials stored in the application.

Temporal audit ledger — financial-grade immutability: The v2.3.0 permanent quarterly audit ledger treats weekly pipeline baselines with the same discipline as signed financial reports. Every confirmed baseline is UUID-keyed, timestamped, and quarter-tagged. INSERT-only — no DELETE, no UPDATE paths exist anywhere in the application code. The strict confirmed_at < asOf SQL guard structurally prevents the "today vs today" diff bug without relying on any convention or developer discipline. The ledger enables SR/SM/Customer trajectory analysis, Next Steps hygiene scoring, and coaching signal detection across every week of a quarter — capabilities that require immutable history to be meaningful.

34/34 test harness as submission evidence: A 13-week in-memory Q3 2026 simulation (scripts/test-baseline-ledger.js) with 20 synthetic opportunities and deterministic weekly mutations proves schema immutability, diff correctness across all change types, Generate-Only exclusion, and calendar math — 34 explicit assertions, zero randomness. Judges can run node scripts/test-baseline-ledger.js on any machine with Node.js and see all assertions pass in under 5 seconds.

Filter-scoped AI narratives: Narratives are generated scoped to whatever filter the VP has applied at that moment — enabling deal-subset narratives for specific stages, geographies, or risk tiers. The AI becomes a contextual analyst, not a batch report generator.

Status-driven, re-entrant workflow: Every action is independently re-runnable at any time — no numbered sequence lock. Reflects how a VP actually works: non-linear, iterative, context-dependent.

Multi-user IBM SSO architecture as innovation: v2.4.0 demonstrates that an IBM intranet app can be built with structurally correct IBM w3id OIDC authentication — using the same session shape, same middleware, and same per-user data model that a real production deployment would use — before a single IBM app registration is approved. The architecture proves it at the code level; swapping in real credentials is an ops step, not an engineering step.

Pipeline Intelligence as a management tool: v2.5.0 introduces the Deal Health Card — a hygiene scoring system built on a management thesis about CRM data: that stale Next Steps, absent close plans, and forecast-to-score mismatches are not data quality problems; they are behavioral signals about the humans working those deals. The engine is rules-based and immediately demoable on real data. The watsonx upgrade path (v2.6.0) is documented in server/hygieneScore.js — swapping in granite-3.3-8b for Next Steps quality analysis and llama-3-70b for per-rep coaching narratives requires changing one function, not redesigning the architecture.

Built entirely with IBM Bob: Every design decision, line of code, and debugging session across 29 sessions was collaborative with IBM Bob. The complete session log is part of the repository — an unedited technical history of an IBM employee and IBM's own AI tool building a production business application together.
