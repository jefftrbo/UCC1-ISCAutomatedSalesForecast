What you actually said (the three use cases, reframed)

The three statements from Session 25 are not feature requests. They are a management thesis — a theory about how pipeline data reveals human behavior. Let me restate each precisely:

1.
SR-SM-C Behavior Over Time
"Track the historical performance of the Sales Rep, Sales Manager, and possibly the Customer's responses/actions/behaviors during the quarterly sales cycle."

Translation: The pipeline isn't just data about deals — it's a behavioral record of the people working those deals. Stage progression, amount changes, close date slippage, Next Steps cadence — these are human behavioral fingerprints encoded in CRM fields. The VP wants to read those fingerprints across a full quarter, not just this week.
2.
Communications Hygiene as a Predictive Signal
"Poor opportunity communications hygiene is an indicator of a sales opp that is not as good as it sounds."

Translation: A deal that sounds great in a forecast call but has stale or absent Next Steps is a liar deal. The hygiene is the tell. You don't need to catch the rep lying — the CRM data does it automatically if you look at the right columns with the right time window.
3.
Absence of Activity as a Coaching / Attrition Signal
"The absence of Next Steps and/or Team Notes is more than likely a symptom of a sales rep that needs coaching, or is possibly in the process of leaving IBM."

Translation: A rep who stops updating the CRM is either checked out mentally or physically leaving. This is a people management signal, not just a data quality problem. The VP needs to act on it — not just see it.

The feature: "Deal Health Card" — a per-opportunity intelligence modal

The concept is a new button in the opportunity table — a small Health icon next to each row — that opens a modal with a full intelligence profile on that deal. Not a diff. Not a score. A managed deal review card that answers: "Should I be worried about this deal, and what action do I need to take right now?"

Modal sections (proposed layout)

Section 1: Deal Header (always visible)

Opportunity name, owner, manager, account, stage, forecast category, close date, amount, AI score/tier. All from the current opportunities row — no new data needed.

Section 2: Hygiene Score Card

A computed 0–100 hygiene score based purely on existing fields — no watsonx required at first. Rules (all buildable today):

●
Next Steps recency exists
Parse the date prefix in next_steps text (e.g. "7/9:", "7/13."). Days since last update → score penalty. Blank = max penalty. >14 days stale = amber. >21 days = red.
columns: next_steps, scraped_at
●
Team Notes presence exists
Binary — does a close plan exist? 98% of Duey's pipeline has blank team notes. This alone is a systemic signal. Presence = +10 pts.
columns: team_notes
●
Forecast call vs AI score alignment exists
If rep calls it "Commit" (implying high confidence) but AI score is Low (<40), that's a "liar deal" flag. If FLM Judgement also disagrees with forecast_category, double flag.
columns: forecast_category, flm_judgement, score, tier
●
Close date slip count requires ledger history
Query baseline_ledger for this opp's historical close dates. Count how many times it moved right. Each slip = hygiene penalty. "This deal has slipped 3 times in Q3" is a coaching talking point.
table: baseline_ledger (already captured)
●
Stage velocity requires ledger history
Weeks since last stage advancement. A deal sitting at "3 - Design" for 6 consecutive weeks is stuck — that's different from a deal at "3 - Design" for 1 week. Stagnation is a risk signal.
table: baseline_ledger (already captured)
●
Amount stability requires ledger history
Has the deal amount grown (good), shrunk (concerning), or oscillated up/down (very concerning — rep is guessing)? Amount volatility is a CRM hygiene problem and a deal quality problem.
table: baseline_ledger (already captured)

watsonx injection points (future-proof from day one)

The rules-based version is v2.5.0. The watsonx version is v2.6.0. The architecture is identical — only the action item text generation swaps from deterministic strings to watsonx.ai LLM output. Every other signal detection, scoring, and UI is unchanged.
△
Next Steps quality analysis watsonx.ai · granite-3.3-8b
Today we detect blank and stale. watsonx can read the actual Next Steps text and assess quality: Is it specific or vague? Does it name a person, a date, a deliverable? "Will follow up soon" scores 10/100. "7/9: Pricing deck delivered to CIO; follow-up call scheduled 7/16 with Wendy Zhao" scores 90/100. Ambiguous language detection — this is exactly what you asked for.
Prompt pattern: "Rate the specificity and actionability of this Next Steps entry (0-100). Flag vague phrases. Extract: named person, date, deliverable. Text: [next_steps]"
△
Close plan completeness watsonx.ai · granite-3.3-8b
Team Notes as a close plan document. watsonx evaluates: Does it have a sponsor? Decision maker? Procurement path? Competitive displacement strategy? IBM value proposition stated? Scores each dimension. A close plan that names a sponsor and a timeline but has no competitive reference is scored "Incomplete - 3 of 5 criteria met."
Prompt pattern: "Evaluate this close plan against 5 criteria: [1] named executive sponsor [2] timeline [3] competitive awareness [4] IBM value prop [5] procurement path. Score each 0-1. Text: [team_notes]"
△
SR behavioral pattern narrative watsonx.ai · llama-3-70b
For the per-rep hygiene view, watsonx generates a coaching narrative paragraph based on the rep's data pattern across the quarter: "Rep X has 8 active deals, of which 6 show no Next Steps activity in the past 3 weeks. Stage progression on 5 deals has stalled at 2-Qualify for 4+ weeks. This pattern is consistent with disengagement. Recommend 1:1 this week." This is the exact kind of signal you described for Use Case 3.
Prompt: feed the rep's deal summary + hygiene stats + week-over-week history into llama-3-70b and ask for a management narrative
△
Deal-level risk narrative for GM slide watsonx.ai · llama-3-70b
Today the GM PPT has bullet points for each deal. watsonx replaces those with a one-sentence risk-adjusted narrative per deal: "Labcorp renewal — rep calls Best Case but score is 28/100, Next Steps are 18 days stale, and close date has slipped twice. Recommend VP call with customer before EOQ."
Already wired in generatePpt.js — swap in the hygiene signals as additional context fields alongside the existing scoring prompt
△
Quarterly trend summary for GM meeting watsonx.ai · llama-3-70b
At Q-end: feed all 13 weeks of baseline_ledger data into watsonx and generate a full quarterly narrative: team performance, individual rep trajectories, deals that moved from Pipeline to Won vs those that slipped out, and a recommended focus list for Q4 pipeline build. This is the SR-SM-C tracking Use Case 1 in its full form.
New endpoint: POST /api/quarterly-summary — aggregates 13 weeks of baseline_ledger, calls watsonx llama-3-70b, returns narrative

Thoughts on the multi-user test approach

You mentioned you'll test each of the 9 users today by setting the ISC filters to their name, pulling a HAR, running Refresh Data, and working the UI. Here's how to maximize the value of that testing session:

What to verify per user

  • HAR load isolation: After loading Jeff's HAR, confirm GET /api/opportunities returns only Jeff's rows — and Duey's 221 are untouched. Use the browser dev tools Network tab while logged in as Jeff.
  • Score action: Run Score for each user. Verify scores are written to that user's rows only — not cross-contaminated. Check ai_scored_at timestamps.
  • Baseline & GM Report: Run the confirm modal for each user. Verify the PPT lands in output/{safeId}/forecast-YYYY-MM-DD.pptx — not in the root output folder.
  • What Changed diff: Each user's diff compares against their own prior baseline — not Duey's. If a user has no prior baseline, diff should return "No previous baseline found" (not an error, not Duey's data).

The one test that matters most for the challenge demo

Log in as Duey. Score. Generate PPT. Logout. Log in as Jeff. Score. Confirm that Jeff sees 0 of Duey's 221 deals. Generate Jeff's PPT. Open both PPTs. They should be completely independent reports — different deal sets, different narratives, different file paths. That is the multi-tenant isolation proof for the judges.

What to watch for (things that could break)

  • HAR filter miss: If the ISC filter wasn't correctly set to each user's name before pulling the HAR, the HAR may contain Duey's full pipeline. The opportunity_owner column will expose this — check that owners match the logged-in user's territory.
  • Session bleed: After logout, clear cookies completely before logging in as the next user. The TEST MODE banner shows the active ibm_id — confirm it changes.
  • Seed data vs HAR data: Users 2–9 currently have 6 seed deals each. Loading a real HAR will add/replace those. The COALESCE logic in load-from-har.js preserves existing user_id on conflict — but new rows from the HAR will be tagged with the USER_ID env var. Make sure that's set correctly before each HAR load.
