The problem it solves

Every week before the US Public Sector IBM GM meeting, a Sales VP manually exports the pipeline from IBM Sales Cloud (ISC), copies deal data into a spreadsheet, writes a narrative summary by hand, and builds a PowerPoint. The process takes 60–90 minutes every single week and is error-prone because it's done under time pressure with no automated change detection.

There is no built-in way to see what changed week-over-week: which deals were promoted, which slipped close dates, which dropped out, which appeared for the first time. That comparison lives only in the VP's memory.

The deeper problem is structural: IBM Sales Cloud is protected by IBM w3id SSO with passkey authentication that blocks every programmatic access attempt. Seven technical approaches were tried and documented — all blocked by IBM's own security model. The data lives behind glass that IBM has not opened to its own employees via API.

Core value proposition: Replace that 90-minute manual process with a single web app that loads the live pipeline, scores every deal with watsonx.ai, surfaces week-over-week changes automatically, and generates the GM PowerPoint in one click — with multi-user IBM SSO and a Pipeline Intelligence Engine that turns CRM data into management action items.

What the app does today (v2.5.0)

  • 🔑
    Sign In — Simulated IBM SSO (v2.4.0)
    Login page at /login — IBM black top bar, w3id-lookalike form. 9 real IBM users (TSLs, ATLs, Sales VP, ATL manager) each with their own isolated pipeline. Session architecture is structurally identical to real IBM w3id OIDC — swapping to production credentials requires changing one code block and setting two env vars.
  • ⟳
    Refresh Data
    Loads 221 live opportunities from ISC via a HAR export — the practical workaround for IBM w3id passkey auth that blocks all programmatic access. Stores to local SQLite in under 2 seconds. Every row is tagged with the authenticated user's ibm_id — no row can be read by another user's session.
  • ⬡
    Score with watsonx.ai
    Every deal gets a confidence score (0–100) and tier (High/Medium/Low) via ibm/granite-13b-instruct-v2 on IBM watsonx.ai. Scores are persisted to SQLite — not computed in memory — so the diff engine can show before/after confidence deltas week over week. Rules-based fallback runs when live credentials aren't available; the app is fully functional in either mode.
  • ♥
    Deal Health Card — Pipeline Intelligence Engine (v2.5.0)
    A ♥ icon on every row opens the Deal Health Card modal — a per-opportunity hygiene intelligence profile. Hygiene score (0–100) from 5 components: Next Steps presence (+35), recency (+25), Team Notes presence (+10), forecast/score alignment (liar-deal detection, +20), FLM Judgement agreement (+10). Auto-generated sentence-level action items (P1/P2/P3) — "Rep calls this Best Case but score is 28/100 — needs interrogation in forecast call." Full Next Steps and Team Notes text. Week-over-week timeline from the audit ledger. A second tab shows the Team Hygiene dashboard: all 76 owners in Duey's pipeline ranked urgent→watch→clean with blank NS count, stale NS count, and forecast mismatch flags. Built on the management thesis that CRM hygiene is a behavioral signal, not a data quality problem.
  • ✍
    Generate Narrative
    meta-llama/llama-3-70b-instruct (hosted on IBM watsonx.ai) writes a GM meeting narrative paragraph + bullet points scoped to whatever filter is currently applied — just Q3 Commit deals, just one geography, just High confidence. Mock mode produces realistic output when live credentials aren't available.
  • ⇄
    What Changed (week-over-week diff)
    Compares the live pipeline against the last confirmed baseline. Surfaces 6 change types: promoted deals, demoted deals, slipped close dates, pulled-in close dates, amount changes, and new/dropped deals — each in a drill-down modal with before/after confidence score delta. ibm/granite-3-8b-instruct generates a narrative delta summary for the PowerPoint "What Changed" slide.
  • 📊
    Baseline & Generate GM Report
    Three-button confirm modal: Cancel / Generate Only (PPT, no record written) / ✅ Confirm & Generate (PPT + immutable UUID-keyed baseline written permanently to baseline_ledger). The confirmed baseline is append-only — no DELETE or UPDATE paths exist. A strict confirmed_at < asOf SQL guard makes "today vs today" diff structurally impossible. PPT output is namespaced per user: output/{ibm_id}/forecast-YYYY-MM-DD.pptx.

How Dushyant (and the team) use it

The app uses a status-driven action bar — five flat buttons, always available, no numbered sequence lock. Each button shows a timestamp chip after it runs (Done · 7:06 AM in green, or amber on failure). This reflects how a VP actually works: non-linear, iterative, context-dependent.

Every session starts at /login. After sign-in, a user chip in the header shows initials, display name, role, and a Sign Out button. A yellow TEST MODE banner confirms the active ibm_id. Each of the 9 users sees only their own deals — Duey's 221 real opportunities are never visible to any other user's session.

v2.5.0 live data (Duey's pipeline, July 18 2026): 221 opportunities · 76 distinct owners · 48 blank Next Steps (22%) · 216 blank Team Notes (98%) · 22 urgent / 8 watch / 46 clean coaching flags from the Pipeline Intelligence Engine. The hygiene gaps are not a data problem — they are the demo. A VP seeing "Rep X: 12 deals, hygiene score 0, no Next Steps updates anywhere" is a viscerally powerful management signal.

The one technical constraint worth knowing

Why HAR export instead of live API sync? IBM Sales Cloud uses Salesforce CRM Analytics protected by IBM w3id SSO with passkey (biometric/device-bound, OS Secure Enclave) authentication. Automated login was attempted across 8 approaches over 5+ hours — Playwright automation, cookie injection, CDP interception, Salesforce REST API, ISC devtools — all blocked by IBM's own security model. The HAR export (DevTools Network tab → Export HAR → save as scraper/isc-export.har) takes approximately 90 seconds and is fully reliable. It is the practical solution until an official Salesforce Connected App or ISC service account is available — which becomes possible once the app is approved as an official IBM AI System via the CIO ServiceNow path.

Transitioning to real IBM w3id SSO

The simulated SSO layer is structurally identical to real IBM w3id OIDC. When IBM app registration credentials are available (Client ID + Secret from IBM identity team), the swap is one code block in one file:

// TODAY (SIMULATE_SSO=true): bcrypt check against users table
// PRODUCTION (SIMULATE_SSO=false): replace with Passport.js OIDC strategy
passport.use(new OIDCStrategy({ issuer, clientID, clientSecret, callbackURL },
  (issuer, profile, done) => done(null, { ibm_id: profile.emails[0].value, ... })
));

// Session shape, all DB queries, requireAuth middleware, and frontend
// are unchanged — only the credential check block is replaced.

All other infrastructure — sessions, data isolation, user chip, TEST MODE banner, per-user queries, namespaced PPT output — works identically in both modes.
